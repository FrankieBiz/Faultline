# Skeptical judge questions

Answer with a recorded job or code/test reference. If evidence does not exist, say so.

| Question | Evidence-based answer boundary |
| --- | --- |
| Why use this instead of fixing the line manually? | The demonstration is about verification and evidence. Do not imply this one-line fixture is difficult for an engineer. |
| Did this happen to you? | Only the builder can supply firsthand experience. Do not invent an incident. |
| Is this continuous production monitoring? | No. The current entry starts a bounded registered scenario on request. |
| How many independent defects can it repair? | One registered seeded defect. Additional scenario references are previews. |
| Does the model actually generate the patch? | Show provider/model and attempt from a live Meta job. A deterministic run does not prove model use. |
| What does Meta add beyond a basic API call? | Structured proposal contract, bounded failure grounding, validation feedback, and independent verification. No fine-tuning or model superiority benchmark is claimed. |
| Does prompt containment prevent all injection? | No. It establishes instruction/data boundaries; deterministic gates and containment remain necessary. |
| What happens to invalid syntax or an out-of-scope patch? | Policy rejects it before candidate execution. Show actual policy tests or a recorded rejected attempt. |
| Why is a Git worktree not a sandbox? | It isolates source changes, not process capabilities. The Linux runtime supplies the execution boundary. |
| Can the candidate change the tests? | Only application exports are visible in its restricted namespace. The trusted browser and HTTP assertions run outside that namespace. |
| How do you know the screenshot and trace are real? | Download the corresponding registered artifacts and inspect the matching execution IDs and hashes. Legacy records without runtime provenance remain unverified. |
| Does green mean deployed? | No. It means the candidate passed the recorded checks and cleanup succeeded. |
| Does a passing test suite prove correctness? | Only for tested behaviors; no general mathematical proof or compliance certification is claimed. |
| What happens when Meta fails? | Configured errors remain errors. Missing credentials select an explicitly identified deterministic provider at startup; there is no silent switch after failure. |
| What stops an endless loop? | At most two attempts, stage/work deadlines, cancellation, and a cleanup reserve. |
| How much money does it save? | No measured customer savings exist yet. Use labeled assumptions for estimates, never realized revenue. |
| How fast is it? | Read the actual recorded job and execution durations. Do not quote historical fabricated timings or an SLA. |
| Does cleanup survive interruption? | Demonstrate lifecycle checks; failed cleanup quarantines admission. Do not infer every platform has been validated. |
| What is the target user? | Backend engineers and QA/reliability teams evaluating bounded repair candidates. Adoption still needs validation. |
| What is the next meaningful experiment? | Unfamiliar defects, stronger holdout assertions, repeated live Meta trials, and an independent sandbox review. |
